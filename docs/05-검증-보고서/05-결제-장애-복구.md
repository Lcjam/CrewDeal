# 결제 장애 복구 시나리오

- 기준: 기획서 v1.10 PAY-01~04, REC-01~02, 11.2~11.5, 17.4
- 작성일: 2026-08-24

## 복구 설계

1. 결제 호출 전 `payment_attempts`와 `READY → PROCESSING`을 같은 트랜잭션에 기록한다.
2. PG 호출은 트랜잭션 밖에서 수행한다.
3. 응답 유실·타임아웃은 `UNKNOWN`으로 저장한다. 실패로 단정하지 않는다.
4. 웹훅(Inbox)·운영자 sync·REC-01 대사가 허용 전이표 안에서 `SUCCEEDED` 또는 `FAILED`로 확정한다.
5. 확정은 `payment.finalized` Outbox를 발행하고, 주문 `PAID`와 원장 기록은 워커가 멱등하게 수행한다.

| 시나리오 | 기대 상태 | 자동 검증 | 2계층 실증 |
|---|---|---|---|
| PG 성공 후 응답 유실 | `UNKNOWN → SUCCEEDED`, 주문 `PAID` | PAY-03·S4-a/b 테스트 | `docker kill` 뒤 웹훅 replay |
| 동일 웹훅 10회 | Inbox·주문 전이·원장 각각 1회 | S3 테스트 | Outbox/Inbox 소비 행 수 대조 |
| 역순 웹훅 | 허용되지 않은 전이는 무시·감사 | PAY-04 테스트 | 필요 시 replay 순서 조작 |
| 결제 확정과 예약 만료 | `SUCCEEDED` 결제는 만료 보호, 늦은 확정은 `EXPIRED → REFUNDING` 자동 환불 | ORD-03·REF-02 테스트 | Compose 재현 가능 |

## 실행과 종료 SQL

```bash
cd app && ./gradlew cleanTest test

cd ../load-test
./scripts/run-compose-kill-recovery.sh
```

실증 스크립트는 두 앱과 공유 DB를 띄운 뒤 `UNKNOWN` 결제를 만들고 `app` 컨테이너를 `docker kill`한다. 재기동·웹훅 replay 뒤 `payment-recovery-invariants.sql`이 다음을 검사한다.

```text
unresolved_payments = 0
succeeded_without_paid = 0
finalization_not_processed = 0
total_violations = 0
recovery_assertion = 1
```

## 거래 발생 시각 대사 정책

기획서 v1.10과 D-031에 따라 성공 결제는 내부 `payments.approved_at`과 PG `processedAt`, 완료 환불은
내부 `refunds.completed_at`과 PG `refundedAt`을 비교한다. 절대 차이 1초까지 허용하고, 1초를 초과하거나
비교 대상 시각 한쪽이 없으면 `OCCURRED_AT_MISMATCH` OPEN 불일치로 기록한다.

시각이나 상태를 자동 보정하지 않으며 OPEN인 동안 정산 지급을 보류한다. 다음 대사에서 1초 이내로 일치하면
기존 cutoff-aware 자동 해소와 감사 로그 경로로 RESOLVED가 된다. V7 마이그레이션이 전용 유형을 DB CHECK에
추가했고, 결제·환불 시각, 1,000/1,001ms 경계, 누락, 자동 해소, 정산 HELD를 통합 테스트가 검증한다.
