## 목적·범위

프론트엔드 계획 §9 "수동 시연"의 절차 5개가 실제로 화면에서 끝까지 도는지 격리된 시연 스택에서
검증하고, 눈으로 본 화면 문구·상태 배지·조작 순서·실측 시간을 기록한다. 대상은 시연 콘솔
(`app/src/main/resources/static/console/**`)과 `ops/demo/seed-demo.sh`, `docker-compose.demo.yml`이며,
백엔드 코드는 손대지 않았다. 선택 항목인 S1-a 관찰도 같은 스택에서 따로 실행했다(아래 "선택" 절).

## 준비

기본 포트(8080/8081)로 그대로 실행하면 다음과 같다(계획 §9 원문):

```bash
# 항상 볼륨까지 지우고 시작한다 — mock-pg는 인메모리, PostgreSQL은 볼륨이라 어긋나면 결제가 막힌다
docker compose -f docker-compose.yml -f docker-compose.demo.yml down -v
docker compose -f docker-compose.yml -f docker-compose.demo.yml up -d --build
./ops/demo/seed-demo.sh   # 시연 직전에 (A의 PENDING_PAYMENT 주문은 10분 뒤 만료)
```

구매자 탭은 `http://localhost:8080/console/index.html`, 운영자 탭은 `http://127.0.0.1:8080/console/index.html`.

**다른 포트로 격리해서 띄우려면** `-p`로 별도 컴포즈 프로젝트를 주고, 포트 4개를 환경변수로 덮어쓴다
(이 보고서의 실측은 이 방식으로 만들었다):

```bash
dc() { APP_PORT=18080 MOCK_PG_PORT=18081 POSTGRES_PORT=15432 PROMETHEUS_PORT=19090 GRAFANA_PORT=13000 \
  docker compose -p crewdeal-demo-verify -f docker-compose.yml -f docker-compose.demo.yml "$@"; }
dc down -v
dc up -d --build app mock-pg postgres
APP_URL=http://localhost:18080 MOCK_PG_URL=http://localhost:18081 ./ops/demo/seed-demo.sh
```

포트를 바꾸면 **장애 주입 패널(`/console/demo/`)의 mock-pg 주소를 반드시 덮어써야 한다** — 아래
"운영 요령"에서 정확한 위치와 값을 기록한다.

## 운영 요령 (실측으로 확인한 것)

- **항상 `down -v`로 시작한다.** 이유: mock-pg는 인메모리라 재기동하면 내부 시퀀스(`pg_N`)가 1로
  돌아가는데, PostgreSQL은 볼륨이라 이전 실행의 `provider_payment_id` UNIQUE 값이 남아 있어 새 결제가
  영구히 막힌다(계획 §7.4·§10). **실측:** `down -v` 없이 `seed-demo.sh`를 이미 쓰던 스택에 다시
  돌려도 스크립트는 거부하지 않고 새 캠페인 A·B를 추가로 만들었다 — 가드 조건은 "스택 재사용"이 아니라
  "`mock-pg confirmRequestCount`가 0인데 PostgreSQL에는 이미 결제가 있는" 불일치 하나뿐이다
  (`seed-demo.sh` 0단계). 이번 재실행에서는 `confirmRequestCount=4`, 기존 결제 4건으로 일치해
  `OK`로 통과했다. 즉 이 가드는 "mock-pg만 따로 재시작해 인메모리가 비었는데 DB 볼륨엔 이전 결제가
  남은" 특정 불일치만 잡아내고, 정상적으로 살아있는 스택에 재시드하는 것은 막지 않는다.
- **시연 직전에 시드한다.** `seed-demo.sh`가 만드는 캠페인 A의 `PENDING_PAYMENT` 주문은 10분 뒤
  `EXPIRED`가 되고, 캠페인 A·B의 `endsAt`은 +2시간이라 자동 종료에 걸리지 않는다.
- **구매자 탭은 `localhost`, 운영자 탭은 `127.0.0.1`.** 세션 쿠키가 호스트 단위라 두 호스트명은
  세션이 분리된다. **실측으로 확인한 추가 사항:** 로그인 화면(`/console/index.html`)은 이미 로그인된
  탭에서는 시드 버튼이 아니라 "이미 로그인되어 있습니다" 세션 패널을 보여준다. **같은 탭에서 다른
  시드 계정으로 바꾸려면(예: 구매자 탭에서 supplier → influencer → buyer1 순서로) 먼저 "로그아웃"을
  눌러야 시드 버튼이 다시 보인다** — 계획 문서에 명시돼 있지 않은 조작 순서라 여기 남긴다.
  ADMIN 계정으로 `localhost`에서 로그인을 시도하면(또는 이미 그 상태로 "계속하기"를 누르면) "구매자
  탭과 세션이 겹칩니다 — `127.0.0.1`을 쓰세요"라는 위험 배너가 뜨고 로그인 전에 멈춘다(코드
  `console/index.html`의 `admin-host-warning` 게이트, 확인함).
- **S7은 같은 캠페인 B를 두 번 쓸 수 없다.** 한 번 `SETTLED`가 되면 대사 시나리오의 대상 선택기(운영자
  탭 `/console/demo/`)가 "OPEN" 캠페인만 보여주므로 목록에서 빠진다(실측: 캠페인 B #2를 SETTLED로
  만든 뒤 선택기에 더 이상 나타나지 않음). **재시연은 `down -v` 후 재기동·재시드로 한다.** 주입 거래는
  mock-pg 메모리에 남아 대사 때마다 다시 집계되고(30분 주기 자동 대사가 새 OPEN 불일치로 다시 등록한다 —
  계획 §7.4), 삭제 API가 없어 `down -v`만이 깨끗한 상태로 되돌린다. 참고로 `down -v` 없이 `seed-demo.sh`만
  다시 돌려 새 캠페인 B(#5)로 S7을 실행해도 통과는 했지만, 대사 실행이 `mismatchCount=4`(이전 B #2에
  주입한 거래 2건이 섞임)를 보고해 화면의 불일치 수가 시연 설명과 어긋난다.
- **mock-pg 포트가 바뀌면 패널 주소를 덮어쓴다.** 장애 주입 패널(운영자 탭·구매자 탭 공통,
  `/console/demo/index.html`) 맨 위 "mock-pg 연결" 카드의 `#pg-url` 입력이 그 위치다. 기본값은
  `<이 탭의 protocol>//<이 탭의 hostname>:8081`이고(코드: `demo/pg.js#defaultBaseUrl`), 이번
  스택처럼 `MOCK_PG_PORT=18081`이면 이 기본값은 틀린다 — 구매자 탭은 `http://localhost:18081`,
  운영자 탭은 `http://127.0.0.1:18081`로 각각 입력하고 "저장·연결 확인"을 눌러야 한다. **두 탭은
  origin이 달라 localStorage(`demo:mockPgUrl`)도 따로 저장된다** — 한쪽 탭에서 저장해도 다른 탭에는
  적용되지 않으므로 탭마다 따로 저장해야 한다(실측: 저장 직후 "연결됨" 배지 확인).
- **UNKNOWN 복구 실행 중에는 운영자 탭에서 sync·대사를 누르지 않는다.** 시나리오 코드가 웹훅 재발사
  직전에 결제 상태를 다시 확인해 `UNKNOWN`이 아니면 곧바로 실패 처리한다(재발사 경로를 보여주지
  못했다는 뜻). 이번 실행에서는 절차대로 운영자 탭을 건드리지 않았고 "재발사 전 상태 재확인 —
  UNKNOWN 유지"로 정상 통과했다.
- **로컬 시연 전용 경고는 로그인 화면과 모든 인증된 화면 양쪽에 있다.** 로그인 화면 상단(`notice--warning`)과,
  로그인 뒤 모든 화면의 공용 헤더(`nav.js`) 아래 줄 "로컬 시연 전용 콘솔입니다. 공개 배포 대상이
  아닙니다" 두 곳에서 확인했다.

## 시연 1 — 캠페인 개설부터 OPEN까지

- **탭·계정:** 구매자 탭(`localhost`)에서 `supplier` → `influencer` 순서로 로그인(로그아웃 후 전환),
  운영자 탭(`127.0.0.1`)에서 `admin`.
- **화면 경로:** 공급사 `상품`(`/console/supplier/products.html`) → 인플루언서 `내 캠페인`
  (`/console/influencer/campaigns.html`) → 운영자 `캠페인 승인`(`/console/admin/campaigns.html`).
- **조작 순서:** 공급사가 상품명 1개 + SKU 2개(옵션명만 입력, 등록)로 상품을 등록 → 인플루언서가 그
  상품을 캠페인 개설 폼에서 선택하고 `startsAt`을 지금+1분으로 지정, SKU별 공급 단가(1,000원)를 채워
  개설 → 목록에서 "심사 제출" 클릭(`DRAFT → REVIEWING`) → 운영자 탭에서 "캠페인 승인" 화면의 필터
  기본 필터(`REVIEWING`)에 보이는 승인 대상 행에서 "승인" 클릭(`confirm()` 대화상자
  수락, `REVIEWING → SCHEDULED`).
- **기대 결과/실제 화면:** 승인 즉시 알림 "캠페인 "…"을(를) 승인했습니다. (상태: SCHEDULED)". `startsAt`
  시각이 되면 1초 스케줄러가 `SCHEDULED → OPEN`으로 바꾼다. `GET /api/campaigns/{id}`를 폴링해 확인—
  승인 클릭 후 **23.9초**에 `OPEN` 확인(`startsAt`을 지금+1분으로 잡았고 폼 작성에 시간이 들어 승인이
  `startsAt`에 가까워진 상태였음). 캠페인 목록 화면에 캠페인 상태 배지 "진행중"(OPEN) 표시.
- **근거:** CAM-02(제출·승인), CAM-03(스케줄러 전이), CAM-05(강제 종료는 시연 4).

## 시연 2 — 주문·결제·원장

- **탭·계정:** 구매자 탭 `buyer1`, 운영자 탭 `admin`.
- **화면 경로:** 구매자 `campaign.html?id=`(시연 1의 캠페인) → `payment.html?orderId=` → 운영자
  `원장`(`/console/admin/ledger.html?orderId=`).
- **조작 순서:** 캠페인 상세에서 SKU 수량 1 입력 → "주문하기" → 결제 화면으로 자동 이동(`orderId` 쿼리)
  → "결제하기" 클릭.
- **기대 결과/실제 화면:** 주문 생성부터 결제 화면 도달까지 83ms. "결제하기" 클릭 직후 배지가 "결제 —
  성공"으로 바뀌고(약 2초 안, mock-pg NORMAL 모드라 즉시 200 SUCCEEDED) 상태 타임라인에 "성공 |
  요청 ID …" 한 줄이 쌓인다. 결제 시도 이력 표에 결제 1건(성공, PG 결제ID `pg_N`, 승인시각). 약 5초
  뒤(outbox 반영) 주문 상태가 "결제대기 → 결제완료"로, SKU 예약이 "예약중 → 확정"으로 바뀐다. 운영자
  탭 원장 화면(주문 orderId로 직접 이동)에서 거래 카드 "결제 · 거래 #N · 근거 PAYMENT #N"이 보이고
  **차변 합계 19,900원 = 대변 합계 19,900원**("이 거래는 차대 일치"). 차변 PG 미수금 19,900원,
  대변은 공급사 지급 예정금 1,000원 + 인플루언서 지급 예정금 1,492원 + PG 수수료 예정금 597원 +
  플랫폼 수익 16,811원(합 19,900원).
- **근거:** PAY-01, LED-01~03, S5, ADR-006.

## 시연 3 — UNKNOWN 복구 (S4-a)

- **탭·계정:** 구매자 탭 `buyer1`(장애 패널), 운영자 탭 `admin`(관찰만, 조작하지 않음).
- **화면 경로:** 구매자 `장애 주입 데모`(`/console/demo/index.html`) — "UNKNOWN 복구 (S4-a)" 카드.
- **조작 순서:** mock-pg 주소를 이 탭 기준으로 덮어써 저장 → "대상 캠페인" 선택기에서 시연 1의
  캠페인 선택 → "실행" 클릭. 시나리오가 자체적으로 주문을 만들고 API로 결제·재발사까지 전부 수행한다
  (버튼 하나로 끝까지 진행되는 자동 시나리오이며, 구매자 콘솔의 `payment.html`을 화면으로 띄우지는
  않는다 — 아래 "문제 해결" 참고).
- **기대 결과/실제 화면:** 실행 타임라인에 순서대로 "사전 준비 → 주문 생성(주문 #5, 총액 19900원) →
  장애 모드 적용(SUCCEED_BUT_TIMEOUT, blockWebhook=true) → 결제 요청(202 UNKNOWN, 결제 #4) → NORMAL
  복구(조기) → 증거 확인 Δ(webhookPendingCount Δ1, payment.unknown Δ1, 둘 다 기대와 일치) → 재발사 전
  상태 재확인(UNKNOWN 유지) → 웹훅 재발사(replayedCount=1) → 결제·주문 확정 대기(5.0초, SUCCEEDED →
  주문 PAID 대기로 이어감) → 결제·주문 확정 대기(1.0초, 주문 PAID 확인) → 종료 정리 NORMAL 복구"가
  쌓이고 최종 판정 "통과". **총 소요 7.3초**(클릭부터 통과까지). 별도로 결제 202 응답 시점에 그
  주문의 `payment.html`을 직접 열어 확인한 결과, 배지는 정확히 "결제 — **확정 대기**"였고 본문은
  "결제 결과가 아직 확정되지 않았습니다(PAY-03 UNKNOWN). 같은 요청을 다시 보내지 않습니다 — 낡은
  202 응답을 재생할 뿐입니다. 자동으로 확인 중입니다…"였다(계획 §9 문구와 일치). 시나리오 종료 후
  운영자 탭 `운영 요약`의 "확정 대기 결제 (UNKNOWN)" 카드는 0으로 확인됐다.
- **근거:** S4-a, PAY-03, PAY-04.

## 시연 4 — 강제 종료·정산·환불·회수

- **탭·계정:** 운영자 탭 `admin`만.
- **화면 경로:** `캠페인 승인`(강제 종료) → `정산`(`settlements.html?campaignId=`) → `결제`
  (`payments.html`, 환불) → `원장`(`ledger.html?orderId=`) → `정산`(회수 배치 확인).
- **조작 순서:** 캠페인 승인 화면에서 상태 필터에 "OPEN"을 추가 체크 → 시연 1 캠페인의 "강제 종료"
  클릭(`confirm()` 대화상자 — 문구: `캠페인 "…"을(를) 강제 종료합니다 (OPEN → CLOSED). 이 시연
  스택은 정산 유예가 0초라 종료 즉시 정산이 시작됩니다. 계속할까요?` — 수락) → 결제 화면에서 상태
  필터를 "성공"만 체크(기본 필터가 "확정 대기"뿐이라 꺼야 보인다) → 해당 결제 행 "이력·조작" →
  "환불" → 사유 입력 → "전체 환불 실행".
- **기대 결과/실제 화면:** 강제 종료 클릭 후 **1.06초**에 캠페인 `CLOSED` 확인. 정산 유예 0초 스택이라
  스케줄러(10초 주기)가 곧바로 대상을 확정해 **7.08초** 뒤 배치 2개(공급사 2,000원, 인플루언서
  2,984원 — 이 캠페인의 주문 2건 합산)가 모두 `완료`(COMPLETED)로 표시됐다(`settlements.html`에
  "유형: 정산" 행 2개). 환불 제출 직후 화면에 "환불 접수됨 — 완료까지 자동으로 확인합니다"와 환불
  표 "요청됨" 행이 뜨고, **3.36초** 뒤 `COMPLETED`로 폴링 종료. `RECOVERY`(회수) 배치는 환불 완료
  약 **2.03초** 뒤 공급사 -1,000원·인플루언서 -1,492원 2건이 자동으로 만들어져 곧바로 `완료`였다
  (`settlements.html`에 "유형: 회수" 행 2개, 금액이 음수로 표시). 원장(`ledger.html?orderId=`)에서
  같은 주문에 `REFUND` 거래(#7)가 정확히 반대 방향으로 쌓인 것을 API로 대조했다(PAYMENT #3: 차변
  PG 미수금 19,900 / 대변 세 계정+수익 19,900 ↔ REFUND #7: 대변 PG 미수금 19,900 / 차변 같은 세
  계정+수익 19,900 — 완전한 반대 분개, 합계 재검증도 19,900=19,900).
- **근거:** CAM-05, SET-01~03, S6, REF-02, LED-01(반대 분개), ADR-006.

## 시연 5 — 대사 불일치 → 정산 보류 (S7, SET-02)

- **탭·계정:** 운영자 탭 `admin`만, 대상은 `seed-demo.sh`가 만든 캠페인 B.
- **화면 경로:** `장애 주입 데모`(운영자 탭) — "대사 불일치 → 정산 보류 (S7, SET-02)" 카드.
- **조작 순서:** mock-pg 주소를 운영자 탭 기준으로 덮어써 저장(구매자 탭과 별도로 저장해야 한다) →
  "대사 시나리오(S7) 대상 캠페인" 선택기에서 캠페인 B 선택("대상 주문: 주문 #2 …자동 선택됨" 확인)
  → "실행" 클릭(`confirm()` — "…불일치 거래를 주입하고 강제 종료합니다. 되돌릴 수 없습니다…" 수락).
- **기대 결과/실제 화면:** 타임라인이 "① 불일치 거래 주입(providerPaymentId=pg_5) → ② 대사 실행
  (run #2, mismatchCount=2) → ② 불일치 유형 확인(2건: DUPLICATE_PAYMENT, MISSING_INTERNAL) →
  ③ 캠페인 강제 종료(CLOSED) → ④ 배치 HELD 대기(8.0초, SUPPLIER #5·INFLUENCER #6 둘 다 "미해결
  대사 불일치 2건"으로 HELD) → ⑤ 불일치 일괄 해결(2/2건) → ⑥ 배치 일괄 해제(2/2건 PENDING 전환) →
  ⑦ 완료 대기(12.1초, 배치 2건 COMPLETED + 캠페인 SETTLED) → 종료 정리"로 진행하고 최종 판정
  "통과". **총 소요 22.1초.** `settlements.html`에서 배치 상태가 `HELD`(보류)를 거쳐 `완료`로
  바뀌는 것, 캠페인 목록에서 상태가 "정산완료"(SETTLED)로 바뀌는 것을 API로 재확인했다.
- **근거:** S7, SET-02, REC-01·02.
- **재사용 관찰(추가 확인):** `down -v` 없이 `seed-demo.sh`만 다시 돌려 새 캠페인
  B(#5)를 만들고 그 위에서 S7을 다시 실행했다 — **통과했다.** 다만 대사 실행 로그가
  `mismatchCount=4`로 나왔다(이전 캠페인 B(#2)에 주입했던 거래가 mock-pg 메모리에 남아 매번 새로
  집계되기 때문 — 계획이 경고한 그대로). 시나리오는 대상 주문(#7)에 걸린 2건만 정확히 골라
  처리했으므로 결과 자체는 영향받지 않았다. 옛 캠페인 B(#2)는 이미 `SETTLED`라 대상 선택기(OPEN
  캠페인만 나열)에서 사라져 다시 고를 수 없었다 — "같은 캠페인 B를 두 번 못 쓴다"는 것은 이 의미다.
  깨끗한 재시연은 `down -v` 후 재시드한다(운영 요령).

## 선택 — S1-a 관찰

구매자 탭 `campaigns.html`(`/console/buyer/campaigns.html`, 1초 폴링)을 띄운 채 부하 스크립트를 돌려
잔여 재고가 100 → 0 → `SOLD_OUT` 배지로 바뀌는 것을 본다 (계획 §9 선택 항목).

```bash
APP_URL=http://localhost:8080 DB_PORT=5432 DB_CONTAINER=<compose 프로젝트>-postgres-1 \
  ./load-test/scripts/run-s1-a.sh
```

스크립트 기본값(`localhost:58080`, `55432`)은 게이트용 스택이라 콘솔에 보이지 않으므로 세 값을 시연 스택에
맞춘다. psql이 없으면 `DB_CONTAINER`가 필요하다(기본 compose 프로젝트명이면 `crewdeal-postgres-1`).

- **실측 (격리 스택, `APP_URL=http://localhost:18080 DB_PORT=15432 DB_CONTAINER=crewdeal-demo-verify-postgres-1`):**
  스크립트 `S1-a PASS` — 주문 1,000건 중 성공 100, 품절 응답 900, 5xx 0. 화면의 "S1-a campaign" 행은
  "개설예정 합계 100개" → (2.1초 뒤) "진행중 합계 100개" → (12.7초 뒤) "진행중 합계 0개" → (2.2초 뒤)
  "품절 합계 0개"로 바뀌었고, 품절 후에도 목록에서 사라지지 않았다(기본 필터에 `SOLD_OUT` 포함 — D-054).
  재고 0과 품절 배지 사이의 약 2초는 재고가 먼저 커밋되고 캠페인 상태는 1초 스케줄러가 뒤따라 맞추는 설계다.
- **부작용:** 시연 DB에 `buyer001~200` 계정과 30분짜리 캠페인이 생기고, 유예 0초 스택이라 그 캠페인은
  끝나면 곧바로 정산된다. 시연 1~5 뒤에 하거나, 끝난 뒤 `down -v`로 초기화한다.

## 문제 해결

| 증상 | 원인 | 대응 |
|---|---|---|
| 로그인 화면에서 원하는 시드 계정 버튼이 안 보이고 "이미 로그인되어 있습니다" 패널만 보인다 | 이 탭이 이미 다른 계정으로 로그인돼 있다 — `index.html`은 로그인 상태면 세션 패널을, 아니면 시드 버튼을 보여준다 | "로그아웃" 클릭 후 다시 원하는 시드 계정 버튼을 누른다 |
| 운영자 탭에서 캠페인 승인·강제 종료 버튼이 안 보인다 | `캠페인 승인` 화면의 기본 필터가 `REVIEWING`뿐이다(승인 대기만 기본으로 보여준다) | 화면 위쪽 상태 체크박스에서 보고 싶은 상태(`OPEN` 등)를 추가로 켠다 |
| 결제 화면에서 특정 결제가 목록에 안 보인다 | `결제` 화면의 기본 필터가 `확정 대기(UNKNOWN)`만 오래된 순으로 보여준다(REC-02 설계) | 상태 체크박스에서 원하는 상태(`성공` 등)를 켠다 |
| 장애 주입 패널의 시나리오 버튼이 계속 비활성 | ① mock-pg 주소가 기본값(`:8081`)인 채로 남아 실제 포트(예: `:18081`)와 안 맞거나, ② 대상 캠페인을 아직 선택하지 않았거나, ③ 로그인한 역할이 시나리오가 요구하는 역할(BUYER/ADMIN)과 다르다 | "mock-pg 연결"에서 주소를 이 탭의 실제 포트로 저장, 대상 캠페인 선택, 필요하면 해당 역할로 재로그인 |
| UNKNOWN 복구(S4-a) 실행 중 화면에서 `payment.html`의 "확정 대기" 배지가 안 보인다 | 이 버튼은 데모 페이지 안에서 API를 직접 호출하는 자동 시나리오다 — 주문·결제·재발사를 모두 이 페이지 스스로 수행하고 구매자의 `payment.html`을 새로 열지 않는다. 시각적 증거는 데모 페이지의 "실행 타임라인"이다 | `payment.html`의 실제 배지를 보려면 시나리오가 만든 주문 ID로 별도 탭에서 `payment.html?orderId=`를 직접 열어야 한다(202 응답 후 웹훅 재발사 전의 짧은 시간 안에 열어야 확인 가능) |
| 환불이 `COMPLETED`로 뜬 직후 원장 화면에 `REFUND` 거래가 아직 안 보인다 | 원장 기록은 결제 확정과 같은 방식으로 outbox 워커가 비동기로 쓴다 — 환불 상태 자체는 먼저 확정되고 원장 반영은 조금 늦을 수 있다 | 원장 화면은 자동 갱신되지 않는다(읽기 전용, 수동 새로고침) — 잠시 뒤 새로고침한다 |
| S7 대상 선택기에 이미 썼던 캠페인 B가 안 보인다 | 선택기는 `OPEN` 캠페인만 나열한다 — 한 번 `SETTLED`가 된 캠페인은 대상이 될 수 없다 | `down -v` 후 재기동하고 `seed-demo.sh`로 새 캠페인 B를 만든다. 재시드만 하면 새 B로도 통과는 하지만 이전 주입 거래가 `mismatchCount`에 섞인다(실측 4건) |
| `seed-demo.sh`가 "`down -v` 후 재기동하세요"로 실패한다 | mock-pg의 `confirmRequestCount`가 0인데 PostgreSQL에는 이미 결제가 있다 — mock-pg만 따로 재시작(재빌드)했을 때 생기는 불일치다 (실측: `restart mock-pg` 뒤 재시드가 "PostgreSQL에는 기존 결제(4건)가 있지만 mock-pg 상태는 비어 있습니다"로 실패) | mock-pg만 재시작하지 않는다. 이미 이 상태가 됐다면 `down -v` 후 재기동해야 한다(결제가 영구히 막히는 것과 같은 근본 원인) |
