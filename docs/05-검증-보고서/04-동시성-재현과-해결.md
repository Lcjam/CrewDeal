# 동시성 문제 재현과 해결 과정

- 기준: 기획서 v1.10 ORD-02·ORD-04·PAY-02·REF-02·SET-02·REC-01, 17.3
- 작성일: 2026-08-24
- 범위: 6주차 재감사에서 발견된 다중 인스턴스 정합성 결함의 코드·테스트 보완

## 문제와 해결

| 문제 | 재현 가능한 경쟁 | 해결 | DB 최종 방어 |
|---|---|---|---|
| REF-02 상태 게이트 | 결제만 `SUCCEEDED`, 주문은 아직 `PENDING_PAYMENT`인 창에 환불 접수 | 일반 환불(`PAID`), 만료 경쟁(`EXPIRED`), 보상 환불 경로를 분리하고 필수 조건부 전이가 0행이면 전체 접수를 롤백 | 기존 유효 결제·환불 부분 유니크 |
| SET-02 동결 | 미처리 Outbox와 미확정 결제를 별도 시점에 읽는 사이 결제 확정 | 결제 생성·확정·정산 결정을 캠페인 행 `FOR UPDATE` 공통 장벽으로 조정 | V6 이전 행은 수정하지 않고 애플리케이션 잠금 순서를 통일 |
| REC-01 자동 해소 | 두 대사 실행이 서로가 방금 본 OPEN 불일치를 닫음 | DB 단일 `RUNNING` 세대, stale 세대 회수, cutoff 안의 대상 발생 시각만 자동 해소 | `ux_reconciliation_single_running`, run fencing |
| 환불 이벤트 재발행 | 두 인스턴스가 PENDING 수 0을 같이 읽고 같은 `refund.requested`를 발행 | `INSERT ... ON CONFLICT DO NOTHING`으로 결과를 원자화 | `ux_outbox_pending_aggregate_event` 부분 유니크 |

이 선택의 상세 대안과 비용은 [ADR-010](../03-설계-결정/10-캠페인-행-정산-장벽.md), [ADR-011](../03-설계-결정/11-대사-직렬화와-cutoff.md), 결정 로그 D-027~D-030에 남겼다. PG 호출에는 장벽을 걸지 않으므로 ADR-003의 “외부 호출 중 트랜잭션 미유지”는 유지한다.

## 자동 테스트 조건

```bash
cd app
./gradlew cleanTest test
```

대응 통합 테스트는 다음을 확인한다.

- `RefundApiTest`: 주문이 `PAID`로 확정되기 전 일반 환불을 거부하고, 이벤트 역순에서도 허용 전이만 수행한다.
- `SettlementFlowIntegrationTest`: 결제 확정과 SETTLING 결정을 맞물리게 해도 빠진 결제가 없는지 확인한다.
- `ReconciliationIntegrationTest`: 단일 RUNNING, stale run fencing, cutoff 밖 최신 OPEN 보존, 재발행 중복 방지를 확인한다.
- `CampaignFlowApiTest`: 캠페인 상태 API의 남은 재고·기간·구매 가능 수량 계약을 확인한다.

## 2계층 실증 절차

단일 JVM의 latch 테스트는 커넥션 풀·인메모리 상태를 공유하므로 두 앱 인스턴스 안전성을 증명하지 못한다. 따라서 아래 2계층을 별도 수행한다.

```bash
APP_PORT=58102 APP2_PORT=58103 MOCK_PG_PORT=58101 POSTGRES_PORT=55435 \
docker compose -p groupdrop-week6-s1b -f docker-compose.yml -f docker-compose.two-instances.yml \
  up -d --build postgres mock-pg app app2

cd load-test && ./scripts/run-s1-b.sh
```

종료 뒤 `load-test/sql/inventory-invariants.sql`이 검증하는 값은 다음과 같다.

```text
inventory_balance_violations = 0
reservation_cross_violations = 0
successful_orders = 100
ordered_quantity = 100
available / reserved / sold = 0 / 100 / 0
```
